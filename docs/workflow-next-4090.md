# 双 4090 后续实验与弹性 SP：run03

run03 延续 [run02](workflow-serving-4090.md)，把 8/16 核编码、深度 0/1/2 预取、Wan/Sana 混合调度和真实 SP1↔SP2 放在同一套冻结输入、数值门槛和累计预算下。入口为 [`docker/run-next-study.py`](../docker/run-next-study.py)，输入生成器为 [`workflow_next_study.py`](../workers/ditserve/evaluation/workflow_next_study.py)，报告规则为 [`workflow_next_report.py`](../workers/ditserve/evaluation/workflow_next_report.py)。

本文记录实现、操作契约及截至 2026-10-22 的实测结果。性能结论仅来自完整配对、数值及容量合格的在线对照；数值诊断和显存诊断不授予性能资格。CPU 契约测试、Gloo 事务测试和原生控制器模拟 worker 测试不能代替真实 GPU 数值验收。语义质量始终为 `unverified`。

## 环境与模型配方

当前驱动只接受两张已核对 UUID 的 RTX 4090。运行时使用准备阶段解析出的不可变 `ditserve:rewrite-runtime` 镜像 ID、离线本地模型和冻结源码，保留 `NCCL_P2P_DISABLE=1`。单卡任务默认使用物理 GPU 1；原生 worker 按 UUID 屏蔽其它卡，其进程内设备为 `cuda:0`，不能据此误认为任务用了物理 GPU 0。

| 内容 | 默认主机位置 |
| --- | --- |
| 仓库 | `/home/zyd/code/ditserve` |
| Docker socket | `unix:///run/ditserve-docker/docker.sock` |
| 只读模型 | `/mnt/ssd0/zyd/model/{wan2.1-t2v-1.3b,sana-sprint-0.6b}` |
| 实验根目录 | `/mnt/ssd0/zyd/ditserve-data/workflow/run03` |
| 冻结修订 | `run03/sources/r001/`、`r002/`…… |
| 归档 | `/mnt/ssd0/zyd/ditserve-data/results/workflow/run03` |

Wan 主比较固定 Wan2.1-T2V-1.3B、480×832、17/33 帧、20 步、CFG=5、CPU FP32 UMT5、DiT FP16/Flash、VAE FP32；Sana 使用 Sana-Sprint 0.6B 的 1024px 图像配方。官方循环验收另有小形状 MATH 用例。主调度对照保持相同初始噪声、请求种子、scheduler、提示词及数学配方，只改变被比较的资源或调度控制；独立数值诊断的算术干预另行标注，并保留原 SP1 参考门槛。

CPU 掩码明确写入每个 worker 配置：Wan 在物理 GPU 0 上使用 `0–7` 或 `0–15`，GPU 1 上使用 `60–67` 或 `60–75`；Sana 分别使用 `16–19`、`76–79`。原生 controller 在启动 worker 后绑定 CPU `59`，cell 记录实际绑定，阶段结束恢复原掩码。这些是当前机器的绑定，不是 A100 通用参数。`text_prefetch_depth` 在 worker 加载模型前进入配置，容量同时计入正在编码和已 ready 的票据；深度 0 使用同步准备，深度 1/2 有界预取。已开始但被取消的 CPU 编码仍占容量，直到实际结束。

## 准备、运行与查看

在仓库根目录执行。首次准备要求目标目录尚不存在：

```bash
cd /home/zyd/code/ditserve
python3 docker/run-next-study.py --run-id run03 --prepare
```

准备会复制测量源码、配置、测试及原生构建依赖，执行 CPU CMake 静态链接构建、ctest 和固定镜像内的二进制启动检查，再将二进制与全部测量源码一起封存。静态链接避免宿主机较新的 glibc/libstdc++ 与固定镜像不兼容，具体编译器和命令写入 `build.json`。准备不启动 GPU 实验。若尚未创建 study/预算、仅有失败的 CPU 构建目录，可用 `--prepare --resume-preparation` 保留旧构建并重建新修订。模型清单要求两个模型都存在；小于等于 16 MiB 的文件记录 SHA256，大权重记录大小与修改时间。不要把大权重的元数据绑定称为逐字节完整性校验。

运行或普通续跑使用同一条命令：

```bash
python3 docker/run-next-study.py --run-id run03 --run
```

入口自动切换到 `study.json` 当前指向的冻结控制器。已有任务保留创建时的测量修订，后续控制器修订不会偷偷改掉旧任务的源码。实验任务串行启动，一个任务内部可以使用两张 GPU。

只执行一个已生成的逻辑 block，并留下可续跑检查点：

```bash
python3 docker/run-next-study.py --run-id run03 --run --only acceptance
```

`--only` 不会自动补跑依赖，也不会自动生成所有后续在线任务。依赖未通过时记录跳过原因；后续任务由完整驱动在相应校准后生成。

查看当前逻辑 block、实际 attempt 与冻结修订：

```bash
python3 - <<'PY'
import json
from pathlib import Path
root = Path('/mnt/ssd0/zyd/ditserve-data/workflow/run03')
study = json.loads((root / 'study.json').read_text())
for job in study['jobs']:
    if not job.get('superseded'):
        print(job['logical_id'], job['id'], job['source'])
print('selections:', study['selections'])
print('budget:', json.loads((root / 'budget.json').read_text())
      if (root / 'budget.json').exists() else 'not started')
PY
```

以下操作不启动 GPU：

```bash
python3 docker/run-next-study.py --run-id run03 --preview
python3 docker/run-next-study.py --run-id run03 --archive
```

`--preview` 刷新进行中报告；`--archive` 要求没有 active 任务，生成最终汇总并验证归档往返一致性。归档使用 `prune=False`，原始失败、迁移包和数值诊断证据继续保留。最终报告可以是 `partial`；`study.status=settled` 仅表示本次控制器结算完成。

自定义 `--root` 必须采用 `DATA_ROOT/workflow/RUN_ID` 结构。启动器绑定该数据根及清单中的模型根；不能依靠调用者临时修改挂载环境变量改变已冻结的输入。

## 修订、恢复与完整 block 重试

每个任务都绑定输入与环境文件哈希、镜像、GPU UUID、测量源码修订和构建二进制。续跑检查实际字节；完成结果的 `run.json` SHA256 也必须匹配启动账本。完成任务校验后跳过，不在原目录覆盖重测。

若实现需要修复，先等运行中的控制器、任务和看门狗退出，完成清理及预算结算，再冻结新修订：

```bash
python3 docker/run-next-study.py --run-id run03 --freeze-revision
```

它添加 `sources/rNNN/` 及绑定清单，预算继续累计；既有任务仍指向旧修订。需要使用修复后的代码重跑某个 block 时，创建新的完整 attempt：

```bash
python3 docker/run-next-study.py --run-id run03 --run \
  --retry-block elastic-pause --only elastic-pause
```

这里 `elastic-pause` 只是示例，必须替换为当前实际任务 ID。第一次重试创建 `elastic-pause-attempt2`；再次重试应将 `--retry-block` 指向当前 attempt，例如 `elastic-pause-attempt2`，而 `--only` 仍使用逻辑名 `elastic-pause`。新 attempt 采用新输入、输出、迁移文件及 profiler 路径；整个配对 block 一起重做，旧 attempt 标记 superseded 并保留，旧成本不退还。

已有不完整 attempt 不会被普通 `--run` 覆盖，记录为 `incomplete_attempt_requires_new_block`。不要用 suite 的 `--retry-failed` 绕过严格恢复。控制器在持有锁时自动调用恢复助手，验证旧启动器身份与本实验唯一容器；无法确认清理完成时不提交新任务。异常遗留的 active 时间保守记至恢复，标记 `recovered_uncertain`。

`screen_depth`、`cpu`、`quantum` 三项选择首次写入 `study.selections` 后冻结。补跑或重试不会自动回选已确定控制，避免旧任务使用八核、新任务使用十六核却混在同一个比较中。更换选择需要显式设计、绑定新的对照；不要手改已测输入、清空 selections 或重置 budget。

## 一个累计八小时预算

整个 run03 共用 `budget.json`，总额固定为 **28,800 秒任务墙钟时间**。双卡任务的一秒扣一秒预算，同时另报 GPU·秒；不能把这两种单位混用。

计入启动、模型加载、预热、测量、GPU 诊断、失败及清理。开发、CPU 构建测试、输入准备和事后报告不占实验任务额度。正常性能观测窗口可以排除冷加载和预热，但累计预算不能排除。

| Family | 初始额度 |
| --- | ---: |
| calibration | 1,800 秒 / 30 分钟 |
| cpu | 4,500 秒 / 75 分钟 |
| mixed | 7,200 秒 / 120 分钟 |
| sp | 9,000 秒 / 150 分钟 |
| confirmation | 3,600 秒 / 60 分钟 |
| extension | 1,800 秒 / 30 分钟 |
| reserve | 900 秒 / 15 分钟 |
| 合计 | 28,800 秒 / 480 分钟 |

前序 family 的余量可顺延；这些额度不是保证执行时间。准入要求可用额度至少覆盖 `1.2 × estimated_seconds + 90`，不足时记为 `complete_block_budget_deferred`。每次任务首次准入时冻结 family 上限，独立看门狗同时执行总预算、family 截止点及清理预留；各任务另有自身超时。`reserve` 是预留额度，不是额外的 GPU 任务列表。

本轮可能只得到完整矩阵的一部分。尤其 CPU 两轮六臂筛选与六个在线配对需要竞争同一 family 预算，不能预称全部完成。在线对照按种子交错执行：种子 3201 的核数/深度对照，再到 3202、3203，避免先耗尽某一类全部重复。最终选择仍要求该控制三个独立配对全部合格。

启动前及运行中约每两秒检查目标 GPU 的外部 compute/graphics 进程。检测到外来工作、监控失效或清理无法确认时停止提交；只清理本实验唯一容器，不关闭桌面或其它用户进程。恢复、重试和源码修订都不重置八小时累计成本。

## 实验顺序与选择规则

| 阶段 | 实际对照与依赖 |
| --- | --- |
| acceptance / cost | 每卡官方循环与块暂停恢复验收；只测主线 17/33 帧 Wan 与 Sana 的 SP1 成本。 |
| calibration-video / calibration-mixed | 视频饱和队列及 80% 图像混合饱和队列，各三次观测；中位吞吐定义各自 `λ0`。 |
| cpu-screen-r0/r1 | 8/16 核 × 预取深度 0/1/2；短英文、中文、截断提示词轮换，四请求、17/33 帧、种子 3101/3102。每臂独立进程，第二轮反转顺序。 |
| cpu-online-* | 深度 1 对 2 固定八核；八核对十六核固定筛选深度。每种控制三个种子 3201–3203，每臂 16 个视频请求，按种子交错，交替反转臂顺序。 |
| quantum-screen | 物理 GPU 1 上的 step、100ms block、300ms block；16 个突发混合请求，使用已冻结 CPU/预取控制。 |
| mixed-* | 双卡 step 与 block；Poisson、突发各三种种子 3301–3303，每臂 40 请求，32 图像与 17/33 帧视频各四个。主线为真实 SP1，block 策略名不代表已启用 SP2。 |
| ablation-* | 种子 3304 的 16 请求突发轨迹，分别关闭 `late_short_ms=2000` 或分块解码，保持其余控制一致。 |
| sp-diagnostic / elastic-* | 下节的分阶段数值门槛；数值诊断与 SP1 性能路径分别记录。 |
| elastic-online | 门槛通过后，比较 step 弹性、step 弹性并预留一张图像卡、block 弹性；初始种子 3503，条件允许再跑 3504/3505，轮换臂顺序。 |
| confirm-* | 主比较每种到达模式有三个完整合格配对后，使用新种子 3401/3402；筛选和确认分开报告。 |
| overlap-* / capacity-81 | P4 17/17 帧先诊断生命周期和容量，再三次正常计时，再单独 Nsight Systems。生命周期不合格或余量不足时，改为两次 81 帧 SP1 容量观察。 |

在线主负载为 `0.8λ0`。同一 block 的两臂共享完整请求、初始种子、到达时间和 deadline；视频专用队列 deadline 为各类服务成本的两倍，混合队列为 2.5 倍。突发轨迹每 80 秒只有前 16 秒接收这一轮到达，具体生成后的时间戳保存在输入中。

筛选深度只在两个 exact 且容量合格的八核筛选重复都显示深度 2 完整四请求墙钟更低时选 2，否则选 1。在线核数/深度选择要求各自三个合格配对，且总吞吐比中位数大于 1；这是预定筛选规则，不是统计显著性证明。若选十六核，其深度保持核数对照实际测过的筛选深度。

量子默认 300ms。只有 100ms 对 300ms 的合格配对达到图像 SLO +5 个百分点或图像 p95 降低至少 20%，同时视频 p50 回退不超过 5%、总吞吐回退不超过 5%，才选择 100ms。

## SP 数值门槛与已实现边界

专用 SP 门槛固定种子 3501/3502、17/33 帧、完整 20 步 scheduler、最大绝对误差阈值 0.05；不因失败放宽阈值。两张卡先产生普通 SP1 参考，核对初始噪声、时间步、逐步 latent 与最终视频的跨卡 exact。普通参考在安装分布式处理器之前生成。

| Block | 检查与通过标准 |
| --- | --- |
| sp-diagnostic | 当前生成器选择 `baseline` SP2 诊断模式；依次检查完整 scheduler 的前缀 1、4、20，每步 latent 和前缀视频误差 ≤0.05。失败记录首个分歧附近及 block/QKV 诊断，后续前缀明确未运行。 |
| elastic-transfer | 先验证各卡 SP1 block 暂停恢复与普通执行 exact；再让真实 SP1 状态在完成第 5 步后从 rank 0 迁到 rank 1，第 10 步后迁回。每步 latent 和最终视频必须与普通 SP1 exact。 |
| elastic-pause | 生产并行 block executor 的固定 SP2 先与普通 SP1 满足 0.05 门槛；再将每步 60 个 CFG block 切为 23+14+23，在累计第 23 个 block（条件分支）和第 37 个 block（无条件分支）后暂停，恢复结果必须与固定 SP2 exact。依赖 SP 诊断与跨卡 SP1 迁移通过。 |
| elastic-resize | 完成第 5 步后 SP1→SP2，第 10 步后 SP2→SP1；逐步 latent 和最终视频对普通 SP1 满足 0.05。 |
| elastic-interleave | 固定 SP2 在选定步骤的前 23 个 block 后暂停，在 rank 0 执行真实 Sana 请求，再恢复 Wan；Wan 与未插入图像的固定 SP2 exact，Sana 与独立图像参考 exact，暂停期间 Wan latent 保持不变。 |

门槛逐级阻断；每个 rank、两个种子和两种帧数必须完整。SP 数值诊断失败不抹掉独立完成的 SP1 服务结果；跨卡迁移等门槛已独立生成，不依赖在线成本画像成功。

生产后端采用请求独立的布局、所有权 epoch 和单调 quantum sequence。固定 SP2 可在块边界暂停，**组大小只在完整 diffusion step 边界改变**。初始状态由源 owner 实际准备后复制，目标不会独立重新编码并生成一份“等价”请求。

`host_file_v1` 明确执行 `source_prepare → target_prepare → commit → finalize`，并提供 `abort/status`。文件发布、哈希、序列化、CPU 中转和目标安装均为真实开销。commit 前目标仅 staging；所有目标确认激活后才释放离开的源副本。commit 后失败不得假装回滚，必须终止该实验 cell。原生控制器在迁移与推进期间保留新旧组并集，所有 active rank 核对 epoch、序号和 block/CFG 游标；最终解码由单一 owner 执行。

当前实现与原生 `real_sp` 路径只支持两个 rank、组 `[0]`、`[1]`、`[0,1]` 和度数 1/2，默认行为保持 SP1。它不是已经通过八卡验收的通用弹性运行时。

## SP 失败后的定向续跑

已有队列结算后，可以在同一累计预算内继续定位 SP 数值差异。继续前保留上一轮汇总和归档快照；2026-10-20 的原始结算位于 `run03/checkpoints/before-sp-continuation-r004/`。旧测量目录、失败数组及冻结输入不覆盖。

诊断实现有变化时，先等 active 任务结束，再冻结修订并运行专用队列：

```bash
python3 docker/run-next-study.py --run-id run03 --freeze-revision
```

## 后续优化与消融设计

2026-10-21 的后续设计。以上 r007–r009 是此前已完成证据；以下完整矩阵中，首批获授权的 SP2 scratch、自适应量子与 17/17 帧 VAE 正常计时已实现，执行范围见本节末尾，其余候选仍待验证。沿用已归档结果、累计预算和原数值/容量门槛，不修改历史任务或已冻结源码。

当前最明确的收益是强竞争下图像尾延迟下降和共享 VAE 解码流的显存节省。短任务保护、分块解码各只有一条轨迹上的机制消融；SP2 的补齐次数下降与动态扩缩容正确性已验证，请求级速度尚未验证。CPU 核数和预取深度的现有在线对照尚不构成合格的性能结论，后续主比较继续固定八核、深度一。

### 优先级一：补齐 SP2 正常计时，再决定何时扩容

先用同一实际后端比较原生 SP1、启用修复策略但直通的 SP1、固定 SP2、完成第 5/10 步后扩/缩容四臂；后三臂显式使用相同修复策略，前两臂单独量化单卡 hook 成本。固定 480×832、17/33 帧、20 步，使用三个预先冻结的新请求种子，平衡四臂顺序；每臂固定两次预热、三次热请求测量。不同种子用于请求多样性，同种子的重复用于估计计时波动，两者分别报告。

计时分成两层：预编码请求的 prepare→DiT→VAE→最终输出，以及包含 CPU 编码的完整请求。每层各臂起止点必须相同；真实迁移、必要同步和输出检查不能省略。逐步张量落盘、参考文件读回、额外副本比较和细粒度 profiler 放到独立正确性/归因运行，不能沿用 r009 验收墙钟充当请求耗时。记录请求 p50、逐步时间、扩/缩容各阶段时间、峰值/稳态显存、分配 GPU·秒和固定两卡实验包络的 GPU·秒。

以测得的收益决定后续策略：剩余可并行步骤节省的时间必须覆盖扩容、缩容和同步成本，并增加事先固定的安全裕量及最短驻留时间，避免反复切换。若需要证明服务吞吐收益，再增加同一两卡预算下的“双 SP1 独立服务”对照；单请求 SP2 对单卡的加速不能代替整个服务系统收益。进入 Wan/Sana 在线弹性调度前，另补修复策略下的 Sana 插入正确性与容量验收，并重新测量 SP 效率和真实迁移成本。

### 优先级二：降低 SP2 修复的实际开销

设计开始时，生产 `linear.py` 仅支持 `native` 和 `full_rows_except_ffn1`；首批新增了 `full_rows_except_ffn1_scratch`。全行补齐 `full_rows_linear` 仍仅存在于诊断路径。若比较 FFN1 豁免的请求级贡献，应先将全行基线接入相同生产路径并通过数值、事务策略绑定和清理检查，不能混用两种 runner 的墙钟。

| 消融臂 | 唯一变化 | 待回答问题 |
| --- | --- | --- |
| R0 | 生产路径全行补齐 | 合格的修复成本基线；需补齐实现和验收 |
| R1 | R0 仅移除 FFN1 补齐 | 已知 12.45% 调用减少能节省多少请求时间 |
| R2 | R1 使用有界输入 scratch 复用，保留输出 clone | 分配、清零和拷贝开销能减少多少，是否增加显存 |

先单独 profile R1，量化 GEMM、清零/拷贝、输出 clone 与主机 hook 开销，再决定是否实现更复杂的融合操作。scratch 按设备、dtype、shape、rank/epoch 和 stream 生命周期约束复用，保留非本地行全零、跨请求隔离与缩容释放；避免为每个 Linear 模块长期保留完整 buffer。去除输出 clone 是后续独立候选，需要重新检查连续性、别名和整块底层存储滞留。所有候选都重新比较原普通 SP1 的逐步 latent 和最终视频，保持原 0.05 门槛并明确是否 exact；数值失败的原生 SP2 只作为失败诊断，不作为合格速度基线。

### 优先级三：确认调度贡献，再加入自适应量子

先在三个预先冻结的新强竞争轨迹上完成下列五臂，保持四视频/二十图像、同一到达时间与 deadline、CPU/预取控制、SP1 数学配方和解码最小粒度一致，轮换臂顺序。旧 3701–3703 是初筛，不能重新标为独立确认。

| 臂 | DiT 粒度 | 短任务保护 | 分块解码 |
| --- | --- | --- | --- |
| S0 | step | 开 | 开 |
| S1 | 300 ms block | 开 | 开 |
| S2 | 300 ms block | 关 | 开 |
| S3 | 300 ms block | 开 | 关 |
| S4 | 300 ms block | 关 | 关 |

S0/S1 隔离 DiT 分块贡献；S1–S4 是保护与解码的 2×2 因子设计，可以检查交互作用，不能把各自百分比简单相加。预算有限时，首批仅做 S1/S2/S3 × 三新种子，确认已有两项消融；S0/S4 属于后续完整矩阵，首批结果不解释交互作用。每条轨迹报告图像等待/响应 p95 与最大值、视频 p50/p95、吞吐、SLO 达成率、全部请求完成情况及实际机制触发。三条轨迹不足以支持稳定的显著性或 p99 结论，先报告每个配对和范围；未触发机制也保留结果，不按收益挑选轨迹。确认主方向以后，再增加普通 Poisson 和更高负载作为泛化实验。

随后独立比较固定 100 ms、固定 300 ms、反馈自适应三臂，保持保护和解码设置相同。自适应只使用已经观察到的到达/等待信息：短图像压力触发后使用 100 ms 量子，在最近一次已到达图像后的 1000 ms 热窗口内保持，静默后回到 300 ms。仅按当前队列是否为空切换，可能在图像立即被派发后失去效果；先用 CPU 回放验证规则确实改变块数，禁止读取未来到达。图像 p95 降低以及视频尾延迟/吞吐回退不超过 5% 是预先登记的候选筛选条件，不是已有结果。

## 迁移到 A100 的具体路径

可迁移的是请求状态和事务协议、精确暂停/恢复实现、有界预取、调度控制、冻结输入与证据规则。4090 的 step/block/编码/解码时间、最优量子、核数选择、显存余量、通信带宽和 SP 扩展比都不能搬到 A100 作为实测值。历史 [A100 预实验](a100_preexperiments.md) 只能作独立背景，不能替代新代码、新配方下的重测。

1. **在目标机重新绑定环境。** 按 [迁移手册](../MIGRATION.md) 准备锁定镜像与模型，检查实际 A100 型号、显存、UUID、PCIe/NUMA/P2P 拓扑及可用 CPU。先选择一张卡，再选择一个明确的双卡 pair；新建对应环境与数据目录。run03 驱动有两张 RTX 4090 检查，不能只改 `--run-id` 或把环境名换为 `a100-8x40g` 就直接运行。
2. **先单卡重复正确性与准入。** 重新运行官方循环、block 暂停/导出/导入、chunked decode、Wan/Sana 混合验收；验证各类峰值、并置缓存、上下文与空闲余量。依据目标机重新设置 CPU 掩码、线程数、进程显存上限和 admitted shapes，不能照抄 4090 的 `0.54/0.40` 分配器上限。
3. **重新校准全部成本。** 测 CPU 编码、GPU prepare、DiT step/block、VAE/chunk、Sana、状态 packet 大小、host_file 导出/导入与完整迁移墙钟。测实际 pair 的 collectives 和所选传输路径；更新成本画像、SP 效率和 resize 成本，再通过三次饱和观测重定 `λ0`。保持相同请求配方做硬件比较时保留原始请求列表；评估目标机策略时另生成并冻结由 A100 成本决定的负载/SLO，两类问题分别报告。
4. **在双 A100 上复跑相同门槛链。** 首先复用 `host_file_v1` 与 host-staged NCCL，检查跨卡 SP1 exact、固定 SP2、SP2 block 暂停 exact、1→2→1、Sana 插入及失败/清理。当前专用 harness 明确要求 `NCCL_P2P_DISABLE=1`；若要启用 A100 P2P，需将新传输配置作为单独受支持的实验变体，重新验收及校准，不能通过取消环境变量冒充已验证路径。
5. **门槛和容量通过后再跑在线对照。** 复用配对轨迹、独立重复、预取和量子选择规则、超时与外部负载保护；重新筛选 A100 核数/深度/量子。A100 使用独立明确授权的实验预算和来源清单，不修改或接续冒充 4090 的结果。
6. **最后单独开发和验收 4/8 卡扩展。** 当前事务参与组、world 初始化和原生控制器明确限制 world size 2，扩大到八卡需要扩展组管理、并发迁移预留、控制一致性及故障清理。固定 Wan1.3B 为 12 attention heads，不能直接按纯 Ulysses 做八等份；SP 度数与模型结构/并行方案要重新设计。八卡机器可以先做已支持 pair 的研究，不等于单请求 SP8 已实现。

如果主模型改为 Wan2.2-TI2V-5B，还需要独立移植模型、scheduler/状态 codec、block 形状校验及 VAE 解码路径，重新建立官方参考与成本画像。当前 Wan2.1-1.3B 的事务框架可复用，固定模型的数值资格不能继承给新模型。[迁移手册](../MIGRATION.md) 中早期“真实 cluster 仅 SP1”的实现状态，应结合本文新增的**实验性两 rank 路径**理解；本文不改变其八卡及新模型仍待实现、验证的边界。
